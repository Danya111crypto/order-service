# Order Service API (Variant A)

Сервіс управління замовленнями та товарами з підтримкою ідемпотентності, валідацією, бізнес-операцією скасування замовлень та перевіркою стану бази даних.

## Технології (Tech Stack)
* **Python**, **FastAPI** — асинхронний REST API фреймворк.
* **SQLAlchemy** — ORM для роботи з реляційною базою даних.
* **PostgreSQL** — реляційна база даних.
* **Docker & Docker Compose** — контейнеризація середовища.
* **Pydantic** — валідація вхідних даних.

## 📌 Описание проекта
В рамках лабораторной работы выполнена полная контейнеризация микросервиса заказов (`order-service`). Все компоненты системы (`api`, `consumer`, PostgreSQL Primary/Replica, RabbitMQ) объединены в единый `docker-compose.yml` с настроенными проверками состояния (`healthcheck`) и поддержкой горизонтального масштабирования.

---

## 🏗 Multi-stage Dockerfile
Для сборки Python-сервисов реализован двухэтапный `Dockerfile`:
1. **Stage 1 (builder)**: Базовый образ `python:3.11-slim` с тулчейном сборки (`build-essential`). Устанавливает зависимости в виртуальное окружение.
2. **Stage 2 (runner)**: Финальный минимальный образ. Содержит только Python-runtime, скопированное окружение `/opt/venv` и исходный код. Для безопасности приложение запускается под непривилегированным пользователем `appuser`.

### Звіт з масштабування споживачів (Лабораторна робота №5)

Для перевірки горизонтального масштабування було запущено 3 репліки воркера:
`docker compose up -d --scale consumer=3`

#### Результати експерименту:
1. **Розподіл навантаження (Round-Robin):** RabbitMQ рівномірно розподілив 3 послідовні події (`order_id=10`, `order_id=11`, `order_id=12`) між трьома контейнерами:
   - `consumer-1` обробив `order_id=10`
   - `consumer-3` обробив `order_id=11`
   - `consumer-2` обробив `order_id=12`
2. **Паралельна обробка:** Усі 3 воркери виконували 5-секундну затримку бізнес-логіки паралельно, що скоротило загальний час обробки трьох замовлень з 15 секунд до ~5 секунд.
3. **Гарантія доставлення та ACK:** Кожен вокер відправив підтвердження `ACK` строго після успішного виконання бізнес-логіки та фіксації події в БД.
